# ZeroX 归档说明

> 项目已归档，不再更新。归档日期：2026-11-25。
>
> **设计与用法不在这里重复。** README 已经写了定位、七条设计取舍、配置项与快速开始；`docs/` 下三份文档分别写配置字段、日志格式和续跑前提。本文只写 README 覆盖不到的部分：项目为什么停在 11-25、停在什么位置、哪些结论能用、哪些不能用。

## 1. 一句话定位

ZeroX 是一个基于模型上下文协议（MCP）的 Java 自动程序修复（APR）agent 实验框架，定位是**可开关组件的对照实验平台**，不是新方法。自我限定的完整表述见 README「项目概述」。

## 2. 项目由来

起因是一次跑不通的复现。

2026-11-10，我部署了 RepairAgent（2024）并让它修 Defects4J 的 `Lang_1`。它跑了 53 分钟，最后是我手动中断的。当时我的判断是"上下文累积撑不住了"。

归档前回头翻日志，发现这个判断站不住。下表是当时的运行记录（未随仓库分发）：

| 项 | 实测 | 含义 |
| :--- | :--- | :--- |
| prompt 峰值 | 7,629 tokens | 模型 `deepseek-chat`（64K 上下文），余量充足 |
| token 走向 | 1,496 → 3,042 → 3,503 → 4,604 → 7,359 → 4,875 → 6,809 → 7,629 | 非单调，无逼近上限的迹象 |
| 补丁落盘 | 15 次 | — |
| 不同的补丁 | **1 个** | 15 次落盘的 `changes_dicts` 逐字相同 |
| 测试执行 | 18 次 | 每次都是同一个 `NumberFormatException: "80000000"` |
| 节奏 | 约 2 分钟一轮 | 高度规整 |
| 终止 | 手动中断 | 两次 `Interrupt signal received` |

那个补丁实际是空操作：它声明第 468 行原本是 `if (hexDigits > 16) { // too many for Long`，随后要求把第 468 行改成**同一个字符串**。第 471 行同理。

**这是工程实现层面的观察，不涉及方法本身的评价。** 在它当时的代码里可以看到四处相关处理：

1. 补丁写入前只校验"是否覆盖了所有标记为 buggy 的行"，**不校验"改完之后与改之前是否不同"**；
2. 落盘函数在"修改行与原文相似度低于阈值"时**静默跳过**该行，不报错、不告警；
3. 无论实际写入还是跳过，返回给 agent 的消息始终是成功；
4. 没有"本次补丁与上次相同"的检测。

结果是：**失败看起来像成功，agent 原地转了 15 圈而没有任何信息告诉它这一点。**

这次经历直接决定了 ZeroX 的取舍方向——补丁必须带锚点、校验失败要显式报错，落盘要能验证"确实变了"，重复尝试要留下可审计的痕迹，状态必须外置到 agent 的即时上下文之外。具体怎么实现的，见 README「设计取舍」。

## 3. 停在什么位置

不列设计清单，只列量级——以下数字都能在仓库里直接核对：

## 4. 一条值得单独带走的结论

七条设计取舍里最容易误读的是"首轮裁剪工具集"，而它恰好附带了一个可迁移的边界条件：

工具的 JSON Schema 随每次请求重发，是固定前缀中占比最高的部分（7 个工具合计 3.2K 字符）。ZeroX 的做法是首轮只发 `run_test`，之后固定为全量。实测前缀 2,670 → 首轮 708 / 其后 1,691 token，26 题批次 3.56M → 3.24M（−9.1%）。

真正可迁移的是它的成本闭式解（推导，非实测）：`Δ账单 = (small − full) + k·full·(1 − d)`。`small` / `full` 分别是裁剪后与全量的前缀 token 数，`d` 是缓存命中带来的折扣，`k` 是批内切换工具集的次数。解 `Δ账单 < 0` 得 `k < (1 − small/full)/(1 − d) ≈ 1.02`——批内只容得下约一次切换；到第二次，省下的 schema 就被缓存重算吞掉：同一段对话里按动作交替工作集时，切换后的首次请求命中率只有 8%。

−9.1% 这个数字本身不关键，关键是它的成立条件。只看百分比，容易把它当成一个 prompt 压缩技巧照搬，而照搬过去大概率是负收益。

## 5. 为什么把定位写低

因为第一层实验的结果不能用。

跑完 Defects4J 的 26 个 Bug，得到 26/26 Fixed、26/26 审计 clean、26/26 复跑 Verified Fixed。但这 26 个里有 21 个的执行记录中出现了 `known bug` / `I recall` / `Defects4J <id> fix` 一类措辞：模型认出这些是公开基准中的已知 Bug，从训练记忆中回忆官方修复，而不是从失败测试与源码现场推理。补丁与官方 developer fix 高度吻合（如 `Chart_1` 的 `dataset != null → == null`、`Lang_51` 补一个 `break`、`Math_70` 的 `solve(min,max) → solve(f,min,max)`）。19/26 一个补丁即命中，全批成本 2 元。

**所以 100% 的修复率与低成本是记忆效应，不是修复能力的证据。** 只有 `Verified Fixed` 这一条结论仍然成立：补丁使测试通过，且没有改测试文件。

基于这一点，仓库做了三处调整：README 注明该批结果不可作为修复率或成本的依据；BENCH30 被标注为已弃用；评测重心转向自建的 20 个样例，并为样例补写了分辨力验收。

## 6. 验证到什么程度

**第一层：公开基准，不可用。** Defects4J 3.0.1，26 题、8 个项目，3.56M token、墙钟约 42 分钟。结论见第 5 节。

**第二层：自建样例，可用但样本小。** 20 个不依赖任何公开基准的 Java 样例，分四批：基础 3 个（单根因 / 双根因 / 空引用 + 堆栈误导）、高难度 5 个（症状不指向根因）、契约型 5 个（根因是跨调用契约）、状态与资源生命周期 7 个（回绕、游标未归零、计数未清零等）。

两道**离线**验收，不需要 WSL 或 API：

| 脚本 | 做什么 | 实测 |
| :--- | :--- | :--- |
| `tools/selftests/case_verify.py` | 把根因换回正确实现，重编译同一份测试；要求 bug 版部分失败、修复版全过 | 17 个高难度样例通过，bug 版失败数 4/3/6/3/6/7/4/6/2/3/2/6/3/2/4/3/5；3 个基础样例按同一标准手工验过 |
| `tools/selftests/case_discriminator.py` | 先在**修复版**上还原正确实现，再注入 32 个"看似合理但语义错误"的变体 | 32/32 被拒绝 |

两个坑值得记下来：变体必须在修复版上注入，在 bug 版上注入会因基线本来就挂而假阳性；另有 7 个候选变体经核对是**等价正确实现**（如 LRU"总是 moveToHead"、校验和"clear 为 no-op"），它们被接受不算漏检，反而说明断言没有过度约束实现细节。

归档前（11-25）做了全量复核：20 个样例逐个 `javac` + 运行，全部编译通过、bug 版全部部分失败；11 个单测脚本全通过（`phases_selftest` 依赖 `mcp` 包，需在 `.venv` 里跑）。

**第三层：端到端实测。** `deepseek-flash`、`temperature=0`，3 个样例（`List_999`、`SessionStore_11`、`RenderService_7`）3/3 修复、84,021 token、38.06 秒。`SessionStore_11` 的双根因须两处同改；`RenderService_7` 的堆栈指向中层解引用点而根因在深层初始化循环，仅加 null 检查仍然失败。n=3，只能说明链路通。

## 7. 能主张什么，不能主张什么

给"想引用其中某个结论"的人准备。上表成立、下表不成立，中间没有模糊地带：

| 可以主张 | 依据 |
| :--- | :--- |
| 锚点校验 + 括号预检能把语法错误挡在落盘前 | 机制在代码里，可离线复现 |
| 前缀裁剪在"批内不切换工具集"前提下使全批 token 成本降低 9.1% | 26 题批次实测，附前提（第 4 节） |
| 自建 20 个样例可作为工具链回归集 | 两道离线验收 + 全量编译 |
| 26/26 的补丁确实让测试通过且未改测试文件 | 审计复跑 |

| 不能主张 | 原因 |
| :--- | :--- |
| 修复率、单题成本 | 26 题批次存在训练数据泄漏；端到端只有 3 题 |
| 上下文策略带来了更高修复率 | 没做过 L1/L2 的开关对照 |
| 搜索范围标注减少了读取量 | 只有动机统计（读取中位 71 行 vs 方法中位 20 行），没做批次对照 |
| agent 在真实 Java 项目上的修复能力 | 20 个样例是 AI 生成的合成样例，单个源文件 18–122 行 |

## 8. 已知局限

1. **不支持跨进程恢复。** 活状态卡和 L2 裁剪保住的是上下文，不是检查点；进程重启会丢失进行中的对话与补丁历史。批量层另有断点续跑（`src/zerox_core/resume.py`：从 metrics 读出已完成的题并跳过），但它只保证"不重跑已完成的题"，不恢复跑了一半的题——两者不是一回事。
2. **样例是合成数据，且与生成者同源。** README 的局限性没提这一条，而它恰恰决定现有结论能信几分：20 个样例由模型生成、我逐个审阅并人工校准，没做人类盲评（HPR）、Pass@1 难度校准或跨模型验证。刻意避开了 off-by-one 这类教科书模式，但"避开"本身仍是主观判断。
3. **小模型能调用工具，不等于能修 Bug。** 本地 4B 级模型工具调用稳定，但在 Lang_1 与 Lang_4 上分别运行 27 与 30 轮，各只调用 1 次 `run_test`、从未调用 `patch_and_log`（详见 README「局限性」）。
4. **覆盖范围有限。** 26 个 Bug 覆盖 8 个项目但均为 ant 构建；难度分布偏向单轮收敛；跨模型、非 ant 项目、未公开 Bug 均未验证。自建样例的规模也远小于真实项目。

## 9. 值得单独取走的零件

README 的「目录结构」说明了每个文件是什么，这里只回答"想复用该抓哪一块"：

| # | 零件 | 位置 | 价值 |
| :-- | :--- | :--- | :--- |
| 1 | 事件流工作日志 | `src/worklog.py` | append-only + blob 内容寻址；`rollback` 前把丢弃事件归档进 `human_audit.jsonl`，测试结果从不被覆盖 |
| 2 | 锚点补丁写入 | `src/zerox_core/patcher.py` | 行号锚点 + 括号配平预检（`source_lex.py` 做掩码）+ 事务提交 |
| 3 | 三层上下文 | `src/zerox_core/context.py` | L1 从事件流重建、L2 按决策轮裁剪、L3 不裁剪；裁剪切在 assistant 边界，避免孤立 tool 消息 |
| 4 | 首轮工具裁剪 | `src/zerox_core/phases.py` | 纯函数、离线可测；有前提条件，不要脱离第 4 节照搬 |
| 5 | 两级事后审计 | `src/audit.py` | 只读日志判 `clean`/`invalid`（秒级），复跑判 `Verified Fixed`；`invalid` 时自动还原被改的测试 |
| 6 | 20 个自建样例 | `case/bugs/` | 不依赖任何基准，单次测试数秒；源码与测试都在工作区外，agent 既看不到也改不到 |
| 7 | 样例分辨力验收 | `tools/selftests/case_discriminator.py` | "注入语义错误变体、全拒绝才算有效"这招对任何评测集都适用 |
| 8 | 系统提示词 | `AGENTS.md` | 与模型行为耦合最紧的一份资产：改工具而不改它，agent 的行为会立刻失配 |
